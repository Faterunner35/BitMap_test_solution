# BitMap_test_solution

Reads and writes 24-bit BMP files and recolours one image using the colours of another. For every pixel of the source image, the program finds the nearest colour that occurs in the palette image, using Euclidean distance in RGB, and writes the result to a new BMP.

```
BitMap_STL <source.bmp> <palette.bmp> <output.bmp>
BitMap_STL                     # demo
```

The demo writes a 640×480 gradient (`gradient.bmp`) and reads it back to check the round trip. It then recolours `sample_1280x853.bmp` with the gradient's colours and writes `sample_in_gradient_colours.bmp`.

## Build

CMake ≥ 3.16 and a C++17 compiler (MSVC 2019+, GCC 8+, Clang 7+):

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```

Visual Studio can open the folder (*File → Open → Folder*), or you can use the original `BitMAp_STL.sln`, which now targets C++17 and includes all the sources. GitHub Actions builds and tests every push with MSVC on Windows and GCC on Linux.

## How it works

**BMP I/O** (`Image.h`, `Image.cpp`)
- **Writing:** `BITMAPFILEHEADER` + `BITMAPINFOHEADER`, 24 bits per pixel, BGR byte order, rows padded to 4 bytes and stored bottom-up.
- **Reading:** uncompressed 24- and 32-bit files with any header version (`BITMAPINFOHEADER`, V4, V5). Pixel data starts at the offset given in `bfOffBits`. Both bottom-up and top-down (negative height) files are accepted.
- **Invalid input:** the signature, bit depth, compression, size and file length are all checked. On a bad file `ReadImage` returns `false` with a message and leaves the image unchanged.
- **Pixel layout:** in memory pixels are row-major, and `y = 0` is the top row.

**Nearest colour** (`NearestColour.h`, `NearestColour.cpp`)
1. Collect the unique colours of the palette image. A photo usually has far fewer unique colours than pixels.
2. Build a k-d tree over them. Each node stores the bounding box of its subtree, and a subtree is skipped when its whole box is farther than the best candidate found so far. Checking only the splitting plane is not enough when queries lie far from the palette. That is exactly the demo's case: the gradient's colours lie on the surface r + g = 1. On the demo, box pruning cut the time from 16 s to about 0.9 s.
3. Search the tree once per unique source colour, and cache the results.

Distances use integer RGB bytes, so no floating-point error enters the comparison.

## Bugs fixed in this version

| # | Where | Problem |
|---|---|---|
| 1 | `Export` | Pixel-data offset (`bfOffBits`) was written as 0 instead of 54, so viewers read the header as pixels. |
| 2 | `Export` | Channels were written as RGB; BMP stores BGR, so red and blue were swapped. |
| 3 | `Export`, `ReadImage` | `4 - (w*3) % 4 % 4` is parsed as `4 - ((w*3)%4%4)`, giving 4 padding bytes instead of 0 when a row is already aligned. |
| 4 | `ReadImage` | Height was read from the width field (bytes 4–7 instead of 8–11). |
| 5 | `ReadImage` | Padding was computed from `m_width` before the header was read, when it was still 0. |
| 6 | `ReadImage` | `unsigned color[3]` (12 bytes) received 3 bytes, so two channels were uninitialised memory. |
| 7 | `ReadImage` | Green was assigned twice and blue never. |
| 8 | `ReadImage` | Pixel index was transposed (`j * width + i`). |
| 9 | `ReadImage` | `bfOffBits` was ignored, so files with V4/V5 headers (like the sample, offset 138) were read from the wrong place. Nothing was validated, so a broken file could read out of bounds. |
| 10 | `main`, `SetColour` | x and y were swapped in `main`, indexing out of range. This was hidden by `SetColour` resizing the vector to 808×800 whenever capacity equalled size. Both are removed. |
| 11 | `Colour::operator=` | Did not return a value on the normal path, which is undefined behaviour. The default operator is used now. |
| 12 | `weighted_distance` | Float channels in [0, 1] were passed as `unsigned char`, truncating to 0 or 1, so every distance was meaningless. |
| 13 | `find_nearest_pixel` | Copied the whole pixel vector on every call. It always returned the first pixel because the iterator never moved, so the output was one flat colour. |
| 14 | `find_nearest_color_forwholeimage` | `new Image(800, 600)` leaked. Its size did not match the 640×480 input. |
| 15 | Algorithm | Brute force over 640×480 × 640×480 pixels is about 9.4·10¹⁰ distance evaluations, which takes hours. It is replaced by unique colours + k-d tree + cache. |
| 16 | Repository | `Image.bmp` had the broken header from bug 1 and was removed. It is regenerated by the demo as `gradient.bmp`. `obraz-A.bmp` was actually a JPEG and is now named `obraz-A.jpg`. `sample_1280×853.bmp` is renamed to ASCII `sample_1280x853.bmp`. The per-user `BitMAp_STL.vcxproj.user` is removed. |

## Tests

`bitmap_tests` (run from the repository root):

1. Write/read round trip for widths 1–9 and 641 (every padding case).
2. Header fields of an exported file.
3. Channel order (BGR) and row order (bottom-up) checked byte by byte.
4. A 32-bit top-down BMP.
5. `sample_1280x853.bmp` (V5 header): six pixels compared with values read independently with Pillow.
6. Missing, non-BMP (JPEG) and truncated files are rejected without changing the image.
7. k-d tree against brute force: 20 000 random queries on random palettes and 4 000 on a palette lying on the surface r + g = 255.
8. `FindNearestColours` end to end: a palette maps onto itself, and every output pixel is a nearest palette colour.
